## What was wrong

Two separate complaints, fixed separately:

1. **Too slow.** The default floor was `0.34 Hz` — 2.9 s per cycle. Speed is
   normally unmeasured, so the floor alone decides the tempo on screen; a first
   glance could not tell Running from idle.
2. **Motion not visible enough.** The ray *texture* was static. Only three
   copies of it were scaled vertically in `0.94…1.00` (≤2 pt on a 30 pt bar),
   so turning 横穿扫光 off left a nearly still picture, and even with it on the
   eye tracked a moving mask rather than the rays themselves.

## What changed

| Area | Before | After |
|---|---|---|
| Default tempo | `0.34 Hz` (2.9 s) | `0.70 Hz` (1.4 s), ceiling `1.10 Hz` |
| Presets | 2.9 / 2.0 / 1.4 / 1.1 s | 2.0 / 1.4 / 1.1 / 0.9 s, one click each |
| Ray motion | static texture + `scale.y` 0.94–1.0 | per-ray height/alpha as a function of time |
| Animated layers | 3 beds + 3 peaks + 3 masks + 2 fields | 1 curtain (+ attention/ambient) |
| Frame cadence | continuous transforms | 16–24 frames/cycle (11–17 fps), discrete CA keyframes |
| Wave strength | none | `waveIntensity` 0.30–1.00 (default 0.75), visual only |
| Travelling light off | crest parked, rays almost still | crest parked, **wave still propagates** |

`SpectrumWaveModel` is the single source of truth: two travelling sine waves
with per-ray phase offsets (`0.072`, `0.27` rad) plus a local crest kernel
(`sigma = 0.28 × lane × 0.56`), the same construction as the V5 lab's
`repaint()`. `SpectrumFrameRasteriser` bakes each phase into one bitmap;
`SpectrumFrameCache` keeps an LRU bounded at 16 MiB; the layer plays the
sequence with one discrete `contents` keyframe animation.

## Timeline defect found and fixed during this pass

The first version of the frame sequence used key times `0/n … (n-1)/n`. A
`contents` keyframe animation whose last key time is below `1.0` falls back to
the layer's *model* value for the rest of the cycle, so the final phase was
never presented and the phase before the seam held for two steps — a hitch
every 1.4 s. `timeline-probe.swift` (offscreen `presentation()` sampling, same
macOS build as the app) reproduces it:

```
scheme=legacy frames=24 cycle=1.43s step=59.5ms
  distinct phases presented: 21/24  missing: [4, 12, 23]
```

The last phase is missing at every frame count tried (3/4, 5/6, 7/8, 10/12,
21/24), so it is systematic, not sampling luck. The timeline now closes at
`1.0` with the first phase repeated as the final value
(`GlassSpectrumRenderer.curtainKeyframeTimeline`); regression test
`test_curtainKeyframes_closeTheLoopWithEveryFrameShownOnce`. Hold jitter that
remains in the probe output is ~10 ms polling noise, not a second defect.

### Measured from those recordings (30 fps, lane = 960 px at 2x)

- **Tempo is real, and matches the setting.** Dominant frequency of the lane's
  brightness over 10 s (autocorrelation, 30 fps): `0.50 → 0.500 Hz`,
  `0.70 → 0.697 Hz`, `0.90 → 0.905 Hz`. No frame drops in the clips.
- **Travelling light on**: the height crest sweeps 774 px — **81 % of the lane**
  in 10 s, ~8 sweeps.
- **Travelling light off**: the crest stays inside 174 px (**18 %** of the lane,
  parked), while **68 % of columns change ray height by >2 px** over the same
  10 s (p95 = 13 px of the 34 px band). The wave still propagates.
- **Not a fence:** adjacent-column height correlation is 0.94–0.96 at 1 px but
  falls to **0.00 at 100 px** (traveler off) — neighbouring parts of the curtain
  move independently. The old design moved in three lockstep groups.
- **Colour priority on the live menu bar**: waiting = yellow band with parked
  curtain; error = red; running+waiting = yellow band **and** the running
  curtain; running+error = red; running+unread = green.
- **Text stays readable:** in every frame the system items over the curtain
  (`Sensor 17W`, `25 KB/s`, the `!` badge) keep full contrast.
